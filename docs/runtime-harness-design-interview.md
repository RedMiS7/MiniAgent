# Runtime / Harness 设计访谈

状态：设计讨论中，仅记录已确认决定；尚未形成完整实现契约。

## 问题与当前阶段

当前 AgentLoop 已串联模型与工具，并处理模型流关闭、工具任务取消及模型轮数限制，但成功历史通过完成事件交付，没有独立可查询的 Run 终态。设计目标是补齐运行管理和复用入口，同时复用已有循环及清理能力。

以 ROADMAP.md 的阶段划分为准：P5 Runtime、P6 Harness、P7 Session。旧 docs/p5-work-breakdown.md 使用历史编号，不作为当前阶段归属依据。本次只收敛设计，不标记任何阶段完成。

## 第一轮已确认决定

用户在第一轮回答：`q1 tau-main q2 Harness可复用 Q3 任务应该取消 Q4 A`。

1. 参考用户本地同级目录 `../tau-main` 的实际实现。此前公开资料仅作为补充，不能假定与本地快照相同。
2. Harness 是可复用入口。每次 Run 默认独立；跨轮历史通过显式 Session 共享，不因复用 Harness 而自动继承。
3. 提前停止运行事件消费应取消任务，避免调用方离开后仍隐含执行工具副作用。第二轮确认以运行作用域退出触发取消并等待清理，见下文。
4. 第一版选择失败后结束 Run，不自动重试或恢复。单个工具的结构化失败仍交回模型，不自动判为 Run 失败。

## 第二轮已确认决定

1. 采用 `async with harness.run(messages) as run` 的运行作用域，作用域内消费 `run.events()`。提前离开作用域时取消未完成的 Run 并等待清理；正常完成后退出不改变成功状态。单独 `break` 不保证异步生成器立即关闭，调用方须退出作用域以落实取消。
2. 单工具失败继续回传模型，由模型决定后续行动。框架不自动重试失败调用，不禁止模型根据工具错误选择后续工具调用；模型异常或执行框架故障才按 Run 失败收尾。保留现有 ToolExecutor 将工具异常转为 ToolResult 的行为。
3. Harness 首版只支持顺序复用；有活动 Run 时拒绝启动第二个 Run。取消请求发出后仍须等待收尾完成，不能立即视为可复用。
4. 首版包含人工审批，策略和交互接入归 Harness。Runtime 负责落实运行取消与清理，不承担审批决策。触发审批的规则、拒绝语义和交互接口已在第三轮确认，见下文。

## 第三轮已确认决定

用户对 Q9–Q11 回答“都按照推荐”。

1. Harness 按工具配置 `allow / deny / ask`：直接允许、直接拒绝、逐次人工审批。首版不增加按参数自动分类的策略系统。模型不能改变授权规则，人工批准不能绕过现有目录和命令访问限制。
2. 人工拒绝只针对当前调用，拒绝原因作为结构化工具结果回传模型；后续调用重新按规则处理。拒绝当前调用不同于取消 Run，不引入会话级永久允许或拒绝记忆。
3. Harness 接收异步审批函数，输入工具名称、调用 ID 和参数，返回批准或拒绝。CLI 实现终端交互，离线测试注入假审批函数，Harness 不直接读取终端。
4. 取消 Run 时必须结束审批等待；未批准的工具不得执行。审批函数异常禁止工具执行并按 Run 故障收尾。普通展示回调不是审批通道，其失败不应改变工具执行事实。

## 理由与取舍

独立 Run 让同一入口服务不同任务时不串用历史和取消目标，代价是调用方必须明确选择共享会话。停止消费即取消，避免事件消费结束后仍有后台副作用；实现不能依赖异步生成器的垃圾回收时机。

第一版不自动恢复，可以先验证终态和取消，不需要立即引入恢复点或副作用重放协议。它不撤销已经发生的文件写入，也不意味着每个工具错误都必然终止 Run。

当前 ROADMAP 的 P6 仍包含重试和恢复要求；本轮只确认“第一版”范围，不推定用户已经授权删除后续要求。该范围关系需要后续澄清。
