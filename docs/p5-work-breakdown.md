# P5 工作梳理

## 范围与目标

P5 将已有 Agent Loop 组合成可复用的运行入口，补齐单次 Run 的状态、限制、取消、资源所有权、工具授权和事件关联。
本次只梳理工作，不实现功能、不修改阶段完成状态。以下是建议拆分，尚未实现的接口名称不是既定公共 API。

假设：继续使用异步、流式、单 Agent 结构；独立 Run 默认不保留上次历史；跨轮 Session 管理留到 P6。
复用表示相同 Harness 实现能通过指令和 Tools 配置运行不同任务，不要求运行中热切换工具或并发调度框架。

## 当前基础与缺口

| 领域 | 当前已有 | P5 需要补齐 |
|---|---|---|
| 执行循环 | AgentLoop 串联模型、工具和消息历史，输出 LoopEvent | 复用循环，不另写一套模型/工具调度逻辑 |
| 步数限制 | max_steps 按模型调用轮数计数；最后一轮不能消费工具结果时不执行工具 | Runtime 统一配置限制并记录终态，避免两套计数 |
| 取消与清理 | Loop 关闭模型流、取消并等待工具任务；命令工具处理取消和进程清理 | Run 的取消入口、调用边界检查、提前关闭流后的可靠状态，以及资源所有权 |
| 结果交付 | AgentCompleted.messages 提供成功历史；失败事件与异常有既定约定 | 无需依赖观察者收到终态事件也能确定 Run 状态、结束原因和成功结果 |
| 组件组装 | CLI 直接创建 Model、Registry、Executor、Loop，并关闭 Model | 将通用组装放入 Harness，提供统一运行入口 |
| 工具授权 | Registry 控制已注册工具；ToolContext 有目录限制和命令开关 | 明确每次运行允许哪些工具，并在实际执行处保证不可越权 |
| 事件 | Loop 汇集 Agent/LLM/Tool 三类事件，Executor 隔离观察者异常 | 关联 Run 和模型轮次；全链路隔离展示回调异常 |

P3 整体仍待复查。旧验收文档早于 Pydantic 迁移和 Loop 实现，不能直接把旧缺口当作当前事实。
P5 开始实现前需核对当前数据交接契约，尤其是成功历史、失败、取消与异常的关系；P3 整体复验仍是单独小任务。

## 建议推进顺序

### P5.1：Run 状态与结果契约

目的：先确定一次运行如何被调用方观察，避免后续取消、清理和回调各自解释“完成”。

- 在 miniagent/agent/ 下定义最小运行状态和转换约定，建议 pending → running → succeeded / failed / cancelled；启动前取消允许 pending → cancelled。
- 区分状态和结束原因：step_limit 属于 failed，取消属于 cancelled，工具单次失败回传模型不自动等于 Run 失败。
- 复用 Message、AgentCompleted.messages 和现有事件；仅在统一入口确有需要时新增最小结果类型，不重复维护历史。
- 明确模型异常继续传播、非异常失败正常结束、取消继续传播取消异常；终态不被后续事件覆盖。
- 提前关闭消费流后，Runtime 仍需可靠收敛状态；不能假设消费者必然收到 AgentCancelled。

验收：状态转换、结束原因和成功历史的离线测试；异常/取消后状态可查询；不把失败历史标为可续接成功结果。

### P5.2：Runtime 的限制、取消和清理

目的：统一控制执行寿命，保留 Loop 中已有且经过验证的清理能力。

- Runtime 管理一次运行的任务与状态，将步数限制传给现有 Loop，沿用“模型轮数”的计数语义。
- 提供取消路径，覆盖模型调用中、工具调用中、两个调用之间和启动前取消；取消生效后不启动新调用。
- 明确消费者提前退出必须关闭流的使用约定；用 finally 等路径保证取消并等待子任务和关闭活动流。
- 按资源寿命分工：Run 关闭自己创建的流和任务；外部注入 Model 由调用方关闭；若 Harness 创建并持有 Model，则在 Harness 关闭时释放，而非每次 Run 后释放。
- 清理失败不得把失败或取消变成成功，也不能无说明地覆盖原始失败；具体传播方式在实现时明确并验证。

验收：步数边界不产生多余工具副作用；取消后无新模型/工具调用；提前关闭可收敛；借用资源不误关，自有资源按约定关闭；重复取消不重复执行或破坏终态。

限制：取消不能回滚已经发生的文件写入等副作用；第三方工具必须配合取消，不能承诺强制终止任意 Python 代码。

### P5.3：Harness 组装与统一运行入口

目的：把 CLI 中的通用组装变为可复用能力，保持配置和初始化集中管理。

- 通过构造参数注入 Model、工具配置及所需依赖，组合 Loop 与 Runtime；优先具体组合，不引入插件容器或通用工厂框架。
- 每次调用建立独立 Run 上下文，隔离状态、消息、步数和取消目标；不在共享 Harness 上保存当前任务历史。
- 明确 Harness 关闭与资源所有权，将创建 Model 的提供商差异继续留在 bootstrap/适配层。
- 保留现有 Loop 接口的必要兼容性，公共接口变化同步更新调用方与测试。

验收：同一实例连续运行两个独立任务不串历史或状态；失败后下一次独立 Run 可正常执行；替换假模型或工具无需修改 Loop/Runtime。

### P5.4：工具授权

目的：让模型看到的工具集合与执行器允许执行的集合一致。

- 使用显式授权集合或仅包含获准工具的运行级 Registry，优先选择能复用现有注册机制的最小方案。
- 未授权工具不出现在模型请求中；模型仍返回该工具名时，执行器拒绝执行并提供明确失败结果。
- 保留 ToolContext 的目录和命令限制；工具名获准不等于绕过操作范围限制。
- 新工具继续通过 extension 注册；不同任务的授权集合互不扩大，不直接改动共享 Registry 造成串用。

验收：获准工具正常执行；未授权调用没有副作用；空工具集合支持纯文本任务；命令默认受限、越界路径仍被拒绝。

限制：本阶段提供运行前授权配置；逐次交互审批属于 P7，工具访问限制不等于操作系统沙箱。

### P5.5：Events 的运行关联与观察者隔离

目的：消费多个运行的事件时能够识别来源，展示故障不会改变执行结果。

- 通过每个 Run 的事件流或绑定上下文的回调关联 run_id；根据 AgentProgress 的模型轮次关联 LLM 增量，工具继续使用 call_id。
- 遵守当前事件契约：不恢复已删除的 RunEvent 包装，不给底层事件追加运行 ID。
- Harness 隔离事件展示回调异常，避免把回调失败当作工具执行失败或触发重试；Runtime 状态更新不依赖回调成功。
- 保持事件顺序和单一终态；不引入事件总线、持久化日志或默认完整对话记录。

验收：两个交错消费的 Run 能正确区分来源与模型轮次；相同局部调用索引不混淆；观察者抛错仍只执行一次工具；失败与取消的状态不丢失。

### P5.6：复用示例与阶段验收

目的：用调用方视角证明 Harness 的价值，而不是仅验证新增类可构造。

- 提供文件摘要和 echo 文本处理两个示例，通过指令和 Tools 配置切换任务。echo 使用简单 extension 工具即可，无需依赖系统命令权限。
- 至少选择两种现有 Model Adapters，以模拟 SDK 响应通过 Harness 完成工具往返，不能只用两个假 LLM 代替适配器验证。
- CLI 改用统一入口，保留现有流式展示、多轮历史及失败退出行为；完整 Session 抽取仍留到 P6。
- 更新使用文档，明确 Run 隔离、关闭方式、取消语义、授权配置和步数计数。

验收：两个示例离线可复现；适配器工具往返和续接状态正确；现有相关测试无回归；逐条核对 ROADMAP 的 P5 验收标准后才标记完成。

## 依赖和取舍

建议按 P5.1 → P5.2 → P5.3 → P5.4 → P5.5 → P5.6 顺序推进，每次只完成一项并补充对应任务文档。
P5.4/P5.5 都依赖稳定的 Run/Harness 入口，拆开有利于分别验证授权和事件行为。
不提前增加 Session 持久化、费用预算、全局超时、多 Agent 调度、自动重试或提供商切换。
取消和资源控制可能需要对 Loop 增加少量边界检查，但模型协议转换和工具自身实现不迁入 Runtime。
