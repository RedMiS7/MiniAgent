# Harness 人工审批契约

状态：Q9–Q11 已确认；整体 Runtime / Harness 设计仍待最终收敛。本次只维护设计与验收场景，不实现功能。

## 要解决的问题

工具可用性、人工许可和实际访问限制是不同的约束。需要明确谁发起审批、如何交付拒绝以及取消如何终止等待，避免把审批写入终端或底层 Runtime，并避免审批失败后意外执行工具。

## 已选择的方案

Harness 按工具配置 allow / deny / ask，使用异步审批函数处理 ask。函数接收工具名、调用 ID 和参数，返回批准或拒绝；具体展示与输入由 CLI 等调用方实现。审批不能覆盖目录和命令访问限制。

人工拒绝只作用于本次调用，带原因的工具结果交回模型，后续调用重新按规则判断。首版不实现永久批准、永久拒绝或按参数自动分类的策略系统。这样能保持接口明确，并用假审批函数独立验证，不需要真实终端或模型服务。

取消 Run 必须取消审批等待，未批准的工具不执行。审批函数异常导致 Run 故障收尾，不能当作普通展示异常忽略，也不能被转换成批准。普通展示回调只报告事实，不参与审批决策。

## 实现时必须验证的边界

- allow 不询问；deny 不执行；ask 在批准前不执行。
- 拒绝结果保持原调用 ID，模型可以继续处理后续任务。
- 同名工具的新调用仍重新应用规则，不缓存上次批准。
- 审批函数异常时工具执行次数为零。
- 审批等待中取消，迟到的批准不能启动已取消 Run 的工具。
- 人工批准后仍执行原有访问限制检查。

以上为本次新增的待实现行为测试场景，不代表已有功能通过验收。
