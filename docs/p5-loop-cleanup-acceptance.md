# P5：Loop 清理边界修复与阶段验收

## 问题

上一轮验收复现了模型流执行抛 LLMError、随后 aclose 抛 RuntimeError 的情况。Loop 的 aclosing 会把关闭错误作为主要异常交给 Runtime，导致模型失败被误记为 execution_error。

同时，提前关闭 Loop 生成器时，如果模型或工具清理失败，外层异常处理还会 yield 失败事件，产生 async generator ignored GeneratorExit，遮住真正的清理错误。

## 实现与取舍

- 模型流迭代和工具任务等待分别保留当前原异常。收尾再次失败时，继续抛出原异常，关闭错误作为 Python 原生显式 cause。
- 没有原异常时，直接传播关闭错误；不能产生成功结果。
- 提前关闭引发 GeneratorExit 时，关闭失败直接向关闭调用方传播。Loop 不再在关闭期间 yield 终态事件，Runtime 根据收尾事实交付最终事件与结果。
- Runtime 收到 AgentCancelled 后继续消费 Loop 到异常传播结束，保留 Loop 原取消异常附带的关闭错误。其他调用边界仍检查取消标记。
- 工具正常返回的结构化失败仍回传模型。只有工具执行框架在收尾时真正抛出的异常才进入该异常链处理；不更改 ToolExecutor 的既有工具失败契约。

不新增包装异常、状态类型或事件类型。运行过程继续通过完整消费 AgentEvent 判断。

Loop 已经捕获并保留的关闭错误通过原异常的 __cause__ 交付。RunResult.cleanup_error 仍只表示 Runtime 自己执行 Loop 流 aclose 时捕获的错误摘要；Runtime 不从任意异常链猜测清理错误。原生异常链不会自动写入结果或日志。

## 验证

先用实际 AgentLoop 搭配假模型流复现原模型异常被关闭异常替换，再修复。

python -m unittest discover -s tests -q：全部 158 项离线测试通过。其中 Runtime 相关 46 项，本次新增 6 项：

- 模型流执行与关闭同时失败，保留原异常对象、模型错误码及关闭异常 cause。
- 模型调用取消与关闭同时失败，保持 cancelled 与唯一取消终态。
- 提前关闭模型流时，实际清理异常能传给 Runtime。
- 模型响应完成但关闭失败时，不交付成功历史。
- 工具任务取消收尾失败时，保留取消原因，不启动第二个工具或下一轮模型。
- 提前关闭工具流程时，交付真实清理异常，不出现 GeneratorExit 的次生错误。

取消异常链在协程抛出位置验证；Python 3.10 跨 Task 等待可能重建 CancelledError，这是 Python 层面的交付限制。测试没有依赖真实模型服务。

## 剩余限制

取消需要模型和工具配合，不能强制终止任意阻塞代码，也不能回滚已发生的工具副作用。关闭抛错时只保证关闭尝试结束且故障可见，不保证资源实际释放成功。

第三方组件在自身内部 finally 中覆盖了原异常、且未按统一接口保留原异常时，Loop 无法可靠恢复该信息。此类内部资源管理仍由组件负责；本次覆盖的是 Loop 能直接观测的迭代、关闭与任务收尾边界。

Harness 的审批、授权、事件关联及恢复策略属于 P6；跨轮会话属于 P7。离线验收不代表真实服务或模型任务效果已验证。
